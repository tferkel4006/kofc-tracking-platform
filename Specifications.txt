Claude Event Tracking Application Instructions
This application will be used by multiple Knights of Columbus councils to schedule events and track activities of the council.  It will also allow members to record their time against the various events and activities.
The application will need to run on iphone, android and web browsers.
The tech stack for the application should include React Native, Expo and an Azure SQL Server database using T-SQL.  If necessary use Next.JS with React for more complex desktop layouts.

Specific entity details:
An event can span multiple days.  Each event should have at least one shift but could have more.  Events are council specific although some events can be affiliated with multiple councils.  Each event has an associated category.  Events are date specific.  
Shifts are date and time specific.  Each shift has a required number of volunteers that need to be signed up for it.  Once the required number of volunteers have signed up for a shift it is no longer available for signup.
Activities are council specific but are not scheduled.  Activities are not shared among affiliated councils.  Members/Admins/Super Admins do not need to sign up for activities in order to record time against them.  Activities can happen on any day.  Each activity is associated with a category.
Time is recorded in fifteen minute increments.  
Branding and Usability:
The application should be branded with the Knights of Columbus branding.  
The functions of viewing events and shifts, signing up for shifts, recording time against a shift, recording time against an activity or viewing council members lists should be optimized for the phone and highly intuitive.  Minimize the number of clicks required.
All other functions including maintaining events, shifts, activities, members, councils, parishes, pastors and all the lookup tables should be optimized for the desktop web application.
Error messages should be highly informative including any contextual data that is relevant.
Security:
The login credentials for each user are stored in the Credentials table.  The password field should be encrypted.  The username should default to the members email.  
There should be a mechanism for a user to change and/or reset their password.  The user should be given the option of using faceid on their phone if appropriate.  
The first time the user accesses the application they should be asked for their email address.  Their member record should already be created in the Members table.  If so, prompt them to enter the password they want to use and then store in Credentials table.  If no record is found for them in the Members table then display a message telling them to contact their admin and provide his contact information.
Allow the user to remain logged in to the application on the phone.
Messaging inside application:
Provide mechanism for asynchronous messaging within the application.  Messaging features:
* Media & Document Attachments: Drag and drop PDFs, design files, images, or spreadsheets directly into the message. These remain permanently available in the chat history for later downloading or previewing.
* Granular Search & Filters: Because reviews happen later, users need to find specific items quickly. Look for tools that let you filter by attachments only, sender, or date range so files don't get lost in the scroll.
* Persistent History: Messages and attachments are saved indefinitely allowing reviewers to log in hours or days later from any device and see the exact context

* Drafts: Write out a comprehensive review or update when it's convenient for you, then save it as a draft for sending later.
* Threaded Conversations: Keep feedback organized. When someone leaves a comment on a specific file, keeping that conversation inside a contained thread prevents the main inbox from getting cluttered.
* Read Receipts & "Mark as Unread": Reviewers can glance at a message and then mark it as unread or flag it for later follow-up so it stays top-of-mind until they have time to respond.
Store messages in the database.  
Allow messaging to individuals, groups of individuals or the entire member list from a specific council.  Allow creation of distribution lists by admin or super admin.

Donation Details
Donations are tracked by council.
Donations can be associated with an event or standalone.
Donation methods include:
Cash
Credit card
Venmo
Zelle
Zeffy
Parishsoft
Physical items
Donation methods are enabled by council.
When presenting donation method options for a new donation it needs to be very easy and quick to pick one, not scrolling through drop down.
Upload and store QR code image files for Venmo, Zelle, Zeffy and Parishsoft in Azure Blob storage which direct donations to the proper account by council.
When recording a donation for Venmo, Zelle, Zeffy or Parishsoft present the QR code on the member’s phone. The member will present the QR code to the donor and the donor will scan it in the appropriate application on their phone, enter an amount to complete the transaction and present the confirmation to the member. At that point the member can record the donation, changing the amount donated if different from default amount and description if different from default and donation type if different from default. Allow them to cancel as well if necessary.
Capture picture of donated physical items, along with description and estimated value.
Events can have multiple donations.
Any member can record a donation.
When recording donations for an event you should only have to specify the event for the first donation, all subsequent donations should be associated with the event until the person indicates the event is over. One possible solution is to have the member open the event on the phone, click Start Accepting Donations, enter in default amount and description.
Multiple people can accept donations for an event at the same time from different phones.
Track donation amount, date, time, method, description(optional), donation type, donor’s name(optional) and event if applicable.
Donations are generally anonymous but if available be able to capture donors name.
There can be a default amount, default donation type and default description for event donations.
Event donations can be made during or after an event.
Donations should be optimized for the phone.
Donation types are council specific.
Build out a Stripe ability to accept credit card donations without an active Stripe merchant account.
Stripe merchant accounts are council specific.
Council specific setting whether to pass on credit card fee and what the percentage is.
